# Browser Storage Schema

The browser storage implementation is spread across the owner modules below; there is not yet a single runtime key registry. This page is the inventory of keys currently read or written by the application. `localStorage` values survive browser restarts. The two `sessionStorage` values are short-lived workflow handoffs and are listed separately.

## localStorage keys

Unless noted otherwise, JSON values are encoded with `JSON.stringify`. Keys owned by `lib/storage.ts` use the storage schema version in `txwatch_storage_version`; preferences, sync state, notifications, and wallet state are currently unversioned and must remain backward compatible or be migrated explicitly.

The contract object is stored in the browser as a local cache even when the API is configured. `webhook_url` is included in this record and in full backups, so treat it as sensitive if it contains credentials. Do not put a webhook signing secret or other credential in browser storage; localStorage is readable by same-origin JavaScript.

Two optional contract fields are web-only until the core supports them (see the assumed-field table in `docs/MOCK_API_STRATEGY.md`):

- `webhook_headers` (#408) holds custom delivery headers. Their values are credentials, stored in `txwatch_contracts` the same way `webhook_secret` is today. This is an existing exception to the rule above, not a pattern to copy. The UI masks values, and CSV exports omit them. Full JSON backups include them, as they do the signing secret. Test deliveries forward only allow-listed names.
- `webhook_format` (#409) is `json` when absent. It selects the body shape (`json`, `slack` or `discord`) and holds no credential.

Alert payloads may carry `delivery_status` (#407) from the core. When it is absent the dashboard shows no delivery status.

### Webhook secret rotation

Rotating a webhook secret must not break receivers that are still deployed with the old secret. The core requirement is that a rotation keeps the previous secret usable for a bounded grace period instead of invalidating it immediately:

- **Grace window.** When the secret is rotated, the outgoing secret is retained as `webhook_secret_previous` together with `webhook_secret_previous_expires_at` (epoch milliseconds), set to the rotation time plus **24 hours**. Both fields live on the contract record in `txwatch_contracts`.
- **Dual signing.** While `webhook_secret_previous_expires_at` is in the future, deliveries are signed with both secrets, producing two `v1=` entries in the signature header. `verifyWebhookSignature` already accepts multiple `v1=` entries, so receivers that still hold the old secret keep verifying. After the expiry passes, only the current secret is used and the previous fields are cleared.
- **Finish rotation.** The UI shows the remaining grace window and a "finish rotation" action. Finishing rotation clears `webhook_secret_previous` and `webhook_secret_previous_expires_at` immediately, so only the current secret signs from then on. Receivers must be redeployed with the new secret before the grace window ends or rotation is finished.
- **Security.** `webhook_secret_previous` is a live signing credential for the duration of the grace window. It is stored in the same place as the current secret and must never be written to browser storage; keep it server-side only. Treat it with the same handling as the current secret and clear it as soon as the grace window ends.
- **Backup/export.** Because the previous secret is a credential, it must be excluded from full backups and exports in the same way as the current webhook signing secret. Restoring a backup must not resurrect an expired previous secret; if a previous secret is ever included, its expiry must be preserved so it cannot extend the grace window.

## Limits and cleanup

- Alert retention defaults to 90 days. Saving a retention setting prunes entries older than that setting.
- The normal `addAlert` path keeps at most 500 alerts per `(contract_id, network)` by dropping the oldest. Bulk alert replacement/import does not pass through that cap.
- Storage size is estimated by summing key and value string lengths at two bytes per UTF-16 code unit. When the estimate exceeds 90% of the 5 MiB target (about 4.5 MiB), alert writes are reduced to the latest 30 days; a non-alert write also triggers a best-effort trim of existing alerts to 30 days.
- If a write throws a recognized quota error, the storage layer prunes using the configured retention period and retries that write once. Other storage failures return/fall through as best-effort failures. The browser's actual quota varies, so these are safeguards, not a guaranteed allocation.

## Change notifications

The browser `storage` event only fires in _other_ tabs, never in the tab that made the write. To keep same-tab UI (for example the dashboard counts after adding a contract) live, every write that goes through `save()` in `lib/storage.ts` also dispatches a `txwatch:storage` `CustomEvent` on `window` with `detail.key` set to the storage key that changed. `onAlertsChange` and `onContractsChange` subscribe to both the custom event (same tab) and the native `storage` event (other tabs), so consumers only need one subscription. Writes that bypass `save()` (for example `pruneOldAlerts`) do not notify.

## Migrations

`CURRENT_STORAGE_VERSION` is defined in `lib/storage.ts`. Migrations are registered in `lib/migrations.ts` by the version they upgrade **to**, and `components/StorageBootstrap.tsx` runs them at startup. Version `0` is unversioned legacy data; v1 is the compatible baseline, and v2 backfills `enabled: true` on contracts.

When changing a persisted shape:

1. Update the owning TypeScript type, storage validation/read/write code, and any import/export representation that includes the field.
2. Add a migration function in the owning storage module (or a focused helper), then register it in `lib/migrations.ts` under the next version number. Make it safe for existing and already-partially-upgraded data.
3. Increment `CURRENT_STORAGE_VERSION` in `lib/storage.ts` to that same number. Add a migration test covering old data and the resulting shape; keep the contiguous-version test passing.
4. Update this inventory, including the key's owner, shape, version, defaults, and any changed limits. Verify import/export and consumers that read the stored value.

Every version from `1` through `CURRENT_STORAGE_VERSION` should have a registry entry. Do not rewrite or remove an old migration: existing browsers need the full upgrade path. Migrations run synchronously, so keep them bounded and avoid network access.

## Known schema drift to resolve

- `WatchedContract` in `types/index.ts` currently omits `enabled`, even though storage writes it and migration v2 backfills it. Keep the type and persisted contract shape aligned when touching this field.
- The contracts page and `lib/contractSort.ts` both use `txwatch_prefs` but accept different `sortBy` values. Reconcile those consumers before expanding the preference schema.
- `components/RetentionSetting.tsx` currently previews old-alert counts by reading the literal key `alerts`, while the canonical alert array is `txwatch_alerts`. That read is not a persisted schema key and does not count the canonical history.

There is currently no webhook-secret key in browser storage. If that changes, document its security and backup/export behavior explicitly before adding it. The rotation fields `webhook_secret_previous` and `webhook_secret_previous_expires_at` are part of the server-side contract record and must not be mirrored into `txwatch_contracts` or any other browser storage key.
